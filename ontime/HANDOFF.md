## 1. 這是什麼 app、給誰用

- **OnTime**：Dicky 自己用的作息紀錄 PWA。記錄出門、通勤、上班、下班、到家、用餐、睡眠，以及外送收入。
- **用戶**：
  - 住在多倫多（時區 America/Toronto，有夏令時間）。
  - 做倉庫夜班和外送（Uber Eats／DoorDash）。
  - 一班經常 **跨過午夜**，常常早上才到家，然後朝早先瞓，星期日放假。
- **用戶最怕的事**：
  - 日期撈亂。
  - 記一筆要填很多格。
  - 結果唔想記，越漏越亂。
- **語言**：
  - 介面是繁體中文，常用動作用廣東話口語，例如「食咗飯」「瞓醒喇」「去瞓」。
  - 用戶喜歡人話、親切的字眼，不喜歡生硬、防禦式的說明。
- **技術**：
  - 純 HTML + JS 模組 + CSS，沒有 build 步驟。
  - 資料存在 IndexedDB，可選 Firebase（Google 登入）同步。
  - 有 service worker 做離線。
- **倉庫**：`hasonk200/claude-mini-store`，資料夾 `ontime/`，主分支 `main`。
  - 同一倉庫還有其他 app，例如臨時版 `commute-log-temp/` 和心晴手帳，**不要碰**。

## 2. 背景：為什麼 app 會變成現在這樣

### 2.1 一開始的問題（2.0–2.30）

用戶改了三十多版，仍然覺得「好難用」。逐項查出來的原因如下。

1. **日期常常錯**
   - 夜班跨午夜，每一筆都要分清兩個日期：
     - 「工作日」：這班算哪一天。
     - 「實際日期」：時鐘上真正是哪一天。
   - 舊版 bug 多，用戶要逐筆對照自己的追蹤 App，所以有「已核對」勾選。
   - 錯得太多，用戶一度另外做了一個 **臨時應急版** 來記。
2. **記一筆太麻煩**
   - 記瞓醒要填四格日期時間。
   - 記食飯要填一張八欄的表，而且入口在首頁最底。
   - 結果瞓醒、食完都唔想補記。
3. **漏記令日期更亂**
   - 工作日是由「起身」開始計的。
   - 漏記睡眠，app 就找不到分界，只能用後備規則（36 小時）去估，日期就更亂。
4. **補一趟返工要行好多步**
   - 舊流程是「工作日 → 類別 → 班次 → 哪一步 → 時間」。
   - 一趟有七個時間，就要行七次。
5. **舊紀錄日期錯了，改不到**
   - 整趟面板一直報「次序不對」。
6. **外觀似玩具**
   - 圓泡泡、很粗的字、萊姆綠、卡通街景。
   - 用戶要「現代、進階、專業」，**不要賽博朋克或深色霓虹**。

### 2.2 由此定下的原則（之後所有改動都照做）

1. **只改「怎樣記、怎樣看、怎樣改」，不改計算規則。**
   - 工作日歸屬、收入、工時都有大量測試，用戶也對過數。
2. **用戶只答「幾點」或「幾耐之前」，日期由 app 推算。**
   - 一覺不會超過 24 小時，所以入睡日期只有一個可能。
   - 整趟七格時間由上而下排，鐘數細過上一格就是隔天。
3. **存之前一定顯示確認。**
   - 要寫出真實日期、時長、計入哪個工作日。
   - 不合理的時間直接擋住，例如重疊、次序倒轉、未到的時間、相隔太耐。
4. **常用的事一撳完成，少用的收起。**
   - 完整表格保留，用來補舊日子。

## 3. 核心概念（改任何東西之前要明白）

- **工作日**：一個工作日由「起身」開始。
  - 睡眠 ≥ 4 小時算一個分界。
  - 找不到分界時，用 36 小時後備規則。
  - 計算在 `js/logic.js`（純函式）。
- **一趟**：七個步驟：出門 → 上車 → 抵達 → 上班 → 下班 → 上車 → 到家。
  - 整趟面板見 `js/views/sheet.js`。
  - 推算邏輯是 `resolveTrip`、`resolveTripDetail`、`tripState`。
- **日期推算**：
  - `lastClockBefore`：「幾點」對應最近的過去時刻。
  - 整趟由上而下，鐘數倒退就是隔天。
- **時段**：`phaseOf(t)` 把一天分成四段，用來決定頁頂顏色：
  - 夜晚：21–5 點
  - 清晨：5–8 點
  - 日間：8–17 點
  - 黃昏：17–21 點
- **類別顏色**：每種紀錄有固定顏色，詳細見 `DESIGN.md`。
  - 工作：橙
  - 外送：綠
  - 通勤：青
  - 用餐：紅
  - 睡眠：紫
  - 起身：晨光橙
  - 到家：草綠

## 5. 設計系統（詳細見 `DESIGN.md`）

- **字體**：IBM Plex Sans + IBM Plex Sans Condensed（數字），放在 `fonts/`。
- **圓角**：卡 18、控件 12、標籤 8；時間帶框 24。
- **主角**：24 小時時間帶，以及跟時段轉色的頁頂。
- **桌面外殼**：深藍側欄。手機用浮起的膠囊分頁列，中間有「＋」。
- **顏色要有意思**：類別、狀態、導覽用色；不是灰底加一隻強調色。
- **陰影**：有方向、柔和。
- **深色模式**：每個時段都有自己的深色版。
- **已刻意保留**：休假和未知格的細線斜紋。這是行事曆的慣例，代表「不排班」。impeccable 偵測器會提示，屬於預期。

## 6. 硬性規則（違反就要退回）

1. **不可以改計算規則**：工作日歸屬、36 小時規則、起床分界、收入、工時、日期推算結果。
2. **涉及時間的改動要有測試**：跨午夜、連續兩晚夜班、夏令時間。
3. **不要閃爍、閃光、跳動的動畫**（用戶說傷眼）。只可以用回應用戶動作的短過渡。
4. **不要賽博朋克、深色霓虹、螢光色**。即使模型名有「neon」，風格也不可以變霓虹。
5. **不要推倒重來**：保留時間帶、時段顏色、類別顏色、IBM Plex、現有版面結構。只做打磨。
6. **流程**：
   - 開分支 → PR → 用戶自己合併。**絕不直接 push 到 main**。
   - 一個 PR 做一類事，方便用戶看。
7. **每次發版**：
   - `sw.js` 的 `VERSION` 加一（下一版是 2.39.0）。
   - 同時更新 `tests/r9-sw-cache-cleanup.test.mjs`：版本號、保留清單、要刪的舊快取清單。
8. **用戶真實資料不可以有任何風險**：
   - 匯入、清除、取代之前要先自動備份。
   - 示範模式用獨立資料庫（`?demo`，DB 名 `ontime-demo`）。
9. **字眼**：
   - 用人話，不要長篇解釋、不要防禦性警告。
   - 常用動作沿用廣東話口語。
   - 同一個動作，掣、提示、通知用同一個名。
10. **誠實報告**：做了什麼、沒做什麼、為什麼，在 PR 寫清楚。

## 7. 怎樣跑、怎樣測、怎樣截圖

```bash
cd ontime
npm test                         # 已設 TZ=America/Toronto；目前 274 個全過
python3 -m http.server 8771      # 打開 http://localhost:8771/index.html?nosw&demo&now=2026-11-18T13:35#/today
```

- 網址參數：
  - `?now=YYYY-MM-DDTHH:MM`：固定「現在」。
  - `?nosw`：不用 service worker。
  - `?demo`：示範資料，不會碰真實資料。
- 路由：`#/today`、`#/timeline`、`#/week`、`#/sleep`、`#/meals`、`#/stats`、`#/settings`。
- **截圖檢查**（之前用 Playwright + Chrome）。每一頁都要看：
  - 闊度：360、390、1440。
  - 淺色、深色。
  - 四個時段：建議 `now` 用 06:30、13:35、19:10、23:40。
  - 不可以有橫向溢出，也不可以有 console error。
- 面板也要截：＋新增、整趟、食咗飯、瞓醒喇、休息、收入。
- 可選工具：impeccable 的偵測器 `npx impeccable detect ontime/`。

  - 資料不齊時，畫面是否仍然有用？

  - 間距、字級、對齊、圓角、陰影是否一致。

  - 數字用等寬對齊。
  - 圖示大小和線條粗細是否一致。
- **回饋**
  - 撳完有沒有明確回應（提示、即時更新、可以復原）？
- **效能感**
  - 開 app、切頁、開面板是否即時？
  - 有沒有跳動或閃一下？
- **無障礙**
  - 焦點框、`aria-label`、讀屏次序。
  - 「減少動態」設定。
  - 對比度至少 4.5:1。

## 9. 已知問題和候選改善（請先驗證，再決定）

### 9.1 真實資料的情況（很重要）

用戶 11/18 的實機截圖顯示：

- 最後一次記錄起身是 **11/7**，之後十日沒有睡眠紀錄。
- 有一個「已抵達 01:42」的舊狀態，但沒有上班紀錄，一直掛著。
- 結果工作日範圍退回「00:00 至 00:00」，時間帶幾乎全灰。

這正是第 2 節講的惡性循環。值得想想：

- 開 app 時，能否 **一次過補返幾日的睡眠**？例如列出每個工作日，逐日問「大約幾點瞓、幾點起」。
- 舊的、掛住的旅程狀態（例如抵達了十幾個鐘也沒有上班）：能否主動問「呢趟係咪冇返工？要唔要結束／刪除？」
- 資料少時，時間帶和統計應該顯示有用的引導，而不是一片灰。

### 9.2 其他觀察到的地方

- **手機一週頁**：週時間軸在 390px 要橫向捲，右邊被截斷，不夠一眼看完。
- **設定頁很長**：可以考慮分組、摺疊或者加小目錄。
- **字眼混合**：
  - 書面語（「已存在這部裝置」「請先返回自己的紀錄」）和廣東話（「瞓醒喇」「記返啱啱嗰覺」）混著用。
  - 需要定一個一致的口吻：建議常用動作和提示用廣東話口語，說明文字用簡短書面語。
- **首頁「下一件事」**：右上角是「用餐紀錄 →」，和標題不太對應。
- **整趟面板在 360px**：個別提示文字可能被截。
- **街景插畫**（`hero.js`）：仍然是舊的卡通風，和現在的設計不太統一。可以考慮重畫成同一套風格，或者維持只作可選。
- **手機頂部**：同步圖示和頭像的意思，新用戶未必一看就明。
- **桌面版首頁右上**：「新增記錄」和側欄的「新增記錄」重複。
- **統計頁**：數字很多，可以考慮先講結論，例如「今個月做了 X 鐘、賺了 X」。
- **一撳就記三粒掣**：在 360px 窄手機時，說明文字很細。
- **未做過真機測試**：
  - iPhone「加到主畫面」後的 PWA 表現。
  - 安全區（瀏海、底部橫條）。
  - Google 同步。
  - 行事曆 `.ics` 提醒。
